# 怎么展示这个项目

> 目标岗位：客户成功 / 实施交付 / AI 应用产品运营。
> 一句话定位：**这是一个「把客户问题变成可运营知识 + 可追踪工单」的系统**，不是炫技的 ChatBot。

## 三、30 秒口头版（电梯稿）

「我做了一个新能源 4S 店的 AI 客服工作台。它把常见咨询做成 69 条结构化 FAQ，客户一问，系统先检索，命中就答并给出处；答不准就问车型和现象；涉及价格承诺、投诉、退订直接转人工建工单。工单有 SLA 倒计时，解决后能一键回写成 FAQ，下次自动命中。现在演示数据里自动解决率 85%、转人工率 13.6%、平均首响 9.5 分钟。」

## 四、2 分钟版（面试官说「展开讲讲」）

按「问题 → 做法 → 结果」讲，中间只提一个技术点：

1. **问题**：4S 店客服每天重复回答续航、保养、定金这类问题；直接丢给大模型，价格和保修口径会乱答，答不上来客户就流失。
2. **做法一（知识治理）**：每条 FAQ 都有同义问法、适用车型、答案来源、负责人、更新时间和状态；待审核不参与检索。
3. **做法二（分流）**：置信度够才答；不够就追问车型/现象；价格承诺、投诉、退订、安全隐患一律人工接管。
4. **做法三（闭环）**：转人工建工单，P0 首响 15 分钟；解决后把标准答案回写成 FAQ 草稿，审核发布。
5. **结果**：看板实时算 8 个指标；飞书多维表格同步给客服主管，不用进后台。

**唯一要讲的技术点**：检索用的是「关键词 + 覆盖度打分」，不是向量检索；大模型只在证据充分时做改写，答案里的数字必须能在证据里找到，否则回退规则答案。这个取舍能讲清，比堆名词有用。

## 五、5 分钟现场演示顺序

1. **看板**（30 秒）：先给结论——14 会话、自动解决率 85%、转人工率 13.6%、平均首响 9.5 分钟、SLA 超时 1 单。
2. **知识库**（40 秒）：搜「维保周期」命中「保养周期」；搜「多少钱」被压到追问区间。
3. **三条提问**（90 秒）：
   - `S7 续航多少` → 直接答 + 出处 + 置信度；
   - `多少钱` → 追问车型（不报价）；
   - `给我个底价` / `我要投诉门店服务态度` → 转人工，P1/P0。
4. **工单**（60 秒）：打开投诉单看 P0 倒计时和超时；改成已解决、填根因和方案。
5. **回写**（40 秒）：生成 FAQ 草稿 → 知识库发布 → 再问一次命中。
6. **飞书**（30 秒，可选）：点「同步到飞书」，打开表看 16 个字段。

**保底**：飞书打不开就跳过第 6 步；网络不稳就全程本地，不依赖外网。

## 六、高频追问与答法

**Q：代码是你自己写的吗？**
A（诚实版，对 CSM/实施岗是加分）：「业务部分是我做的——需求梳理、69 条 FAQ 的内容、SLA 规则、演示流程；开发是我用 AI 结对完成的，架构和取舍我能讲清楚，也能现场改阈值、加一条 FAQ。这个项目主要是证明我能把客户问题拆成可落地的方案。」

**Q：为什么不用大模型直接答？**
A：价格、保修、退订不能由模型自由发挥；现在是检索 + 证据 + 数字校验，模型只做改写。

**Q：数据是真的吗？**
A：品牌和车型是虚构的，FAQ 按真实 4S 店话术手工整理，演示会话走真实链路生成，不是写死的假数据。

**Q：指标怎么算的？**
A：自动解决率 =（采纳 + 修改后发送）/ 已审核；转人工率 = 转人工建议 / AI 建议总数；每次点开会话都能看到原始状态，可核对。

**Q：如果客户量很大怎么办？**
A：FAQ 上千条时把 FTS5 换成 pgvector 混合检索；工单和飞书同步已经是解耦的，加队列就行。

**Q：你这个和市面上的客服机器人有什么区别？**
A：区别不在「能聊」，在「答错兜得住」——知识有负责人和更新时间，答不了转人工，解决了会回写知识库，这三件事形成闭环。

## 七、不要这样说

- ❌「我做了 RAG 向量检索」——实际是关键词检索，会被问穿；
- ❌「精通 Python / 全栈开发」——岗位不对口，反而暴露短板；
- ❌ 只讲技术不讲业务——你的岗位要的是「让客户用起来、用得住」；
- ❌ 说「数据是真实的客户数据」——涉及隐私和诚信。

## 九、架构与取舍怎么讲

### 架构：三层回答

- **一层（30 秒）**：前端单页 → REST 接口 → 服务层 → 决策层（知识库 + 规则）→ SQLite / 飞书。
- **二层（2 分钟）**：`POST /api/chat` → `nlu.analyze()` 抽意图/车型/情绪/风险 → `kb.search()` FTS5 召回 + 覆盖度打分 → 冲突检测 → 四路分流 → 落 `messages`（带完整决策 JSON）→ handoff/no_hit 自动建工单（带 SLA 时限）。
- **三层（追问）**：说得出文件、函数、字段。置信度公式在 `app/kb.py:search()`；SLA 在 `tickets.sla_first_due / sla_resolve_due`；审核状态机在 `service.review_message()`。

### 取舍：六个「A 不选 B，因为 C，代价 D，规模到 E 换 B」

| 选择 | 为什么不选另一个 | 代价（主动说） | 何时会换 |
|---|---|---|---|
| 关键词检索（FTS5）+ 覆盖度打分 | 向量检索不可解释、没法现场调阈值 | 同义说法要靠手工写进 variants | FAQ 上千条、说法发散时上混合检索 |
| 规则拼接 + 大模型只改写 | 模型直答会编价格、保修期、优惠 | 回答不够灵活 | 刻意保留的护栏，不换 |
| 阈值 0.62 / 追问线 0.30 | 宁可多问一句，不敢乱答 | 转人工率偏高（13.6%） | 知识覆盖提升后可下调 |
| SQLite 单文件 | 单机演示零配置，不装数据库 | 并发差、无法多实例 | 多人同时使用时换 PostgreSQL |
| 飞书单向下发 | 双写必然冲突，主从必须明确 | 飞书侧改了不回传 | 飞书成为主存储时反向同步 |
| 原生 JS 单页 | 免 npm、免构建，一个人维护 | 组件复用差 | 多人协作时换 Vue/React |

## 十、现场两个 30 秒动作（比说十句管用）

**动作 1：改配置看行为变化**

把 `.env` 的 `A4S_CONF_THRESHOLD` 从 0.62 改成 0.80，重启，再问「保养多少钱」：
置信度 0.768，阈值 0.62 时直接答，0.80 时变成追问。说明「保守程度」是真实可调的业务旋钮。
（诚实说明：改 `.env` 需重启 10 秒，不是热更新。）

**动作 2：改内容看立即生效**

知识库新建一条「试驾车能上高速吗」→ 状态「待审核」→ 搜这句话：最高 0.343，命中不相关条目；
点「发布」→ 再搜：0.97，第一条就是新条目。说明内容可现场增删、发布即生效，且「待审核」不参与检索。
