# 架构说明

## 分层

```
静态工作台 (static/)                     ← 原生 JS，四个标签页
      │ fetch JSON
REST 层 (app/api.py)                     ← 18 个接口，Pydantic 校验
      │
服务层 (app/service.py)                   ← 会话、发消息、审核、反馈
      ├── 决策 (app/answer.py)            ← 检索 + 置信度 + 分流
      │     ├── NLU (app/nlu.py)          ← 意图/车型/情绪/风险/信息完整度
      │     └── 知识库 (app/kb.py)         ← FTS5 召回 + 覆盖度打分 + 冲突
      ├── 工单 (app/tickets.py)           ← 建单、SLA、解决、FAQ 回写
      └── 看板 (app/metrics.py)           ← 实时聚合，不落宽表
      │
SQLite (data/app.db)                     ← faq / sessions / messages / tickets / events
```

API 层不写业务，服务层不碰 HTTP：`app/seed.py` 的演示数据也调用同一个服务层，所以看板上的每个数字都能量出对应代码路径。

## 数据模型

| 表 | 作用 | 关键字段 |
|---|---|---|
| `faq` | 结构化 FAQ | 分类、标准问题、同义问法(JSON)、车型、场景、答案、来源、负责人、更新时间、状态、标签、命中数 |
| `faq_fts` | FTS5 检索索引（trigram） | 只索引「生效」条目；草稿不可被检索 |
| `sessions` | 会话 | 客户、渠道、车型、场景 |
| `messages` | 消息与 AI 决策 | 角色、意图、情绪、置信度、状态、命中的 FAQ、完整决策 JSON、反馈 |
| `tickets` | 工单 | 16 个业务字段 + 首响/解决 SLA 时限 |
| `events` | 审计流水 | 建单、审核、反馈、发布 |

`messages.decision` 存整份决策（证据、风险原因、追问清单），前端「AI 决策面板」直接回放，面试时可以逐条解释 AI 为什么这么答。

## 一次提问的时序

```
POST /api/chat
  → nlu.analyze(text)              意图/车型/情绪/风险/缺什么信息
  → kb.search(text)                FTS5 召回 → 覆盖度打分 → Top3 证据
  → 冲突检测（前两条高分但答案不一致）
  → 分流：
      风险高 / 冲突 / 无命中 → handoff（建工单）
      置信度 < 追问线        → clarify（追问车型、现象）
      追问线 ≤ 置信度 < 阈值 → clarify
      置信度 ≥ 阈值          → answered（答案 + 出处）
  → 落 messages（AI 消息状态 pending / clarify / handed_off / no_hit）
  → handoff / no_hit 自动建单（含 SLA 时限与优先级）
```

客服动作：`accepted`（采纳并发送）、`edited`（改完再发）、`rejected`（驳回，建单）、`handed_off`（主动转人工）。
客户反馈：`solved` / `unsolved` / `wrong`，后两者若无工单会自动补建。

## 打分口径

置信度 = `0.55 × 标准问题覆盖 + 0.25 × 同义问法覆盖 + 0.08 × 标签覆盖 + 0.05 × 答案覆盖 + 车型加权`

- 「覆盖」= 问题被字段命中的比例，按 **0.7 × 二字片 + 0.3 × 单字** 计算（容忍「可以上门试驾吗」这类语序变化）；
- 完全等于标准问题 → 0.90 起；完全等于某条同义问法 → 0.86 起；
- 提到车型而条目是另一车型 → −0.12；条目是「全车型」→ +0.07；
- 3 字以内的问题（「多少钱」「首保」）封顶 0.60，落到追问区间。

所以「多少钱」不会瞎报一个价格，而是问「哪款车」；「S7 多少钱」才会直接答价格区间。

## 为什么不用纯大模型

1. 价格、保修、退订这类口径不能由模型自由发挥 —— 必须引用知识条目并留痕；
2. 4S 店的问题高度重复，FAQ 检索的准确率足够且成本极低；
3. 答不上来时，转人工比编一个答案更符合业务。

M2 接入 DeepSeek 时，模型只负责「把 Top3 证据改写成客服口吻」，系统提示里强制「只能依据给定资料」，生成后再过一次校验：答案中的数字必须能在证据里找到，否则降级为规则拼接。
