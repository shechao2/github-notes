# 项目手册：完整操作 · 构造流程 · 工具 · 角色

> 这份文档回答四个问题：**系统怎么用、当初怎么搭的、需要什么工具、我在里面做了什么**。
> 适合面试前过一遍，也适合交接给别人。

## 一、系统怎么用（五种角色，五条操作路径）

### 1. 客户侧（最终用户）

```
提问 → AI 判断：
  ├─ 置信度够 → 直接回答 + 显示依据（来源 / 负责人 / 更新时间）
  ├─ 置信度不够 → 反问「哪款车、什么现象」，不硬答
  ├─ 知识没有 → 不猜，直接转人工
  └─ 价格承诺 / 投诉 / 退订 / 安全类 → 强制转人工（P0/P1）
→ 回答后客户可反馈：已解决 / 未解决 / 答案错误
```

### 2. 客服侧（工作台）

1. 打开 http://localhost:8000 → 「工作台」；
2. 左侧选会话（或点「+ 新会话」建一个），中间是聊天；
3. 输入客户问题 → 右侧「AI 决策面板」出现：意图、车型、情绪、风险、置信度、命中证据；
4. 三种处理：
   - **采纳并发送**（AI 答得对）
   - **修改后发送**（答得差不多，人工润色）
   - **驳回 / 转人工**（答错了或不归 AI 管）→ 自动建工单
5. 客户反馈后，反馈记录进指标。

### 3. 工单侧（人工客服）

1. 「工单」页，按 P0 → P1 → P2 排序；
2. 点开工单：看客户原话、AI 召回条目、AI 回答、转人工原因、**SLA 首响倒计时**；
3. 状态改「处理中」→ 自动打首次响应时间；
4. 解决时必填：**根因分类**、**最终解决方案**、**满意度评分**；
5. 点「生成 FAQ 草稿」→ 知识库多一条「待审核」，不参与检索。

### 4. 知识侧（内容负责人）

1. 「知识库」页：按分类/状态筛选，或直接搜索（会走检索打分）；
2. 「待审核」的草稿逐条核对：来源是否可查、数字是否有依据、车型对不对；
3. 点「发布」→ 状态变「生效」，重建检索索引，下次同样问题自动命中；
4. 政策变更时把旧条目标「停用」而不是删除，保留追溯。

### 5. 运营侧（每周 30 分钟）

1. 「看板」页看 8 个 KPI：会话量、自动解决率、转人工率、FAQ 命中率、满意度、平均首响、工单未结数、SLA 超时；
2. 看「故障现象分布」：哪类问题最多（车机 / 保养 / 充电…）；
3. 打开「Bad Case 清单」：未命中、客服驳回、客户反馈错误，按原因分派；
4. 看「Top 10 未命中」补 FAQ，看「重复转人工」判断是内容问题还是规则问题；
5. 写 5 行周报（模板在 `docs/sop.md`）。

### 6. 管理员（初始化与配置）

```bash
python -m app.seed                     # 重建演示数据（14 会话 / 5 工单 / 69 条 FAQ）
python -m app.main                     # 起服务（或 uvicorn）
python -m pytest -q                    # 66 个测试

python -m app.feishu init              # 新建多维表格 + 会话表 + 工单表
python -m app.feishu init-tickets      # 只补工单表
python -m app.feishu sync              # 同步会话 + 工单（按 ID 去重）
python -m app.llm "S7 续航多少"         # 验证大模型改写
```

阈值现场可调：`.env` 里 `A4S_CONF_THRESHOLD=0.62`（回答线）、`A4S_CLARIFY_THRESHOLD=0.30`（追问线）、`A4S_LLM=0/1`（大模型开关）。

## 二、项目是怎么构造的（10 步，附顺序和时间）

| # | 步骤 | 具体动作 | 产出 | 用时 |
|---|---|---|---|---|
| 0 | **定边界** | 只做「售前咨询 + 售后维保」两类；只做 3 款车；不做支付、不做真实渠道对接 | 一页需求：角色、场景、指标、不做什么 | 2 小时 |
| 1 | **设计字段** | 定 13 个字段：分类/标准问题/同义问法/车型/场景/故障现象/答案/来源/负责人/更新时间/状态/标签/优先级 | `docs/faq-spec.md` 字段规范 | 2 小时 |
| 2 | **写知识库** | 按真实 4S 店话术写 69 条：售前 28、售后 33、边界 8；每条都有来源和负责人 | `data/faq.json` | 1 天 |
| 3 | **做检索** | SQLite FTS5（trigram）召回 + 覆盖度打分：0.55 标准问题 + 0.25 同义问法 + 0.08 标签 + 0.05 答案 + 车型加权；冲突检测 | `app/kb.py` | 半天 |
| 4 | **做分流** | 四条路：直接答 / 追问 / 不猜 / 转人工；风险词表 + 强制转人工意图 + 信息完整度判断 | `app/nlu.py`、`app/answer.py` | 半天 |
| 5 | **做工单** | 16 字段 + P0/P1/P2 SLA（15 分钟 / 30 分钟 / 2 小时）+ 状态机 + 超时判定 | `app/tickets.py` | 半天 |
| 6 | **做看板** | 8 个 KPI + Top 意图 / 未命中 / 重复转人工 / 故障现象 / Bad Case，全部实时算 | `app/metrics.py` | 半天 |
| 7 | **做回写** | 工单解决 → 生成 FAQ 草稿（待审核）→ 审核 → 发布 → 生效；草稿不参与检索 | `create_faq_draft` / `publish_faq` | 2 小时 |
| 8 | **接飞书** | 建自建应用 → 开 `bitable:app` → **发布版本** → 建两张表（会话 16 字段 / 工单 16 字段）→ 按 ID 去重写入 | `app/feishu.py` | 3 小时（含权限审批） |
| 9 | **接大模型** | 只让模型改写 Top3 证据；数字必须在证据里出现，否则回退规则答案；`NEED_HANDOFF` 升级 | `app/llm.py` | 2 小时 |
| 10 | **测试与交付** | 66 个测试（检索/决策/工单/指标/接口/飞书/LLM）、5 篇文档、5 张截图、演示脚本 | `tests/`、`docs/` | 1 天 |

**总时长**：从零到能演示约 **4—5 个工作日**（每天 6 小时，含学习和踩坑）；如果熟悉 Python + FastAPI，纯编码约 **10—12 小时**。

**关键顺序**：先做 0—2（业务），再做 3—4（判断逻辑），最后才是 5—10（工程化）。**知识库没定下来就写代码，后面全是返工。**

## 三、需要哪些工具（按环节）

### 开发

| 工具 | 用途 | 成本 |
|---|---|---|
| **Python 3.13** | 主语言 | 免费 |
| **FastAPI + Uvicorn** | REST 接口与本地服务 | 免费 |
| **SQLite（内置 FTS5）** | 数据存储 + 关键词检索，不用装数据库 | 免费 |
| **原生 HTML/CSS/JS** | 单页工作台，不需要 npm/构建 | 免费 |
| **pytest + httpx** | 66 个自动化测试 | 免费 |
| **VS Code**（或任意编辑器） | 写代码 | 免费 |

### 外部服务

| 工具 | 用途 | 成本 |
|---|---|---|
| **飞书开放平台**（自建应用 + 多维表格） | 会话/工单同步给客服主管；需要 `bitable:app` 权限并**发布版本** | 免费（企业版） |
| **DeepSeek API** | 把证据改写成客服口吻 | 约 0.1 分 / 次，演示花几分钱 |
| **GitHub** | 代码托管、仓库展示 | 免费 |

### 演示与素材

| 工具 | 用途 |
|---|---|
| **Edge / Chrome** | 打开 http://localhost:8000 演示 |
| **Windows 自带录像（Win + G）** | 录 90 秒演示视频 |
| **PowerShell / Git Bash** | 跑命令 |
| **curl** | 快速验接口（可选） |

### 替代方案（面试时可能被问）

- 向量检索：Chroma / FAISS / pgvector（FAQ 上千条时再上，现在 FTS5 够用且可解释）；
- 数据库：PostgreSQL（要并发和多实例时）；
- 前端：Vue/React（要多人协作时）；
- 部署：Docker + 云主机（要公网访问时）。

**我是这个项目的业务负责人：定义问题、设计规则、写知识库内容、定验收标准；开发部分用 AI 结对完成，架构和取舍我能讲清楚，也能现场改配置和内容。**

### 不是我的部分（诚实说明）

- 代码是我用 AI 编程工具结对写的，不是我从零手敲；
- 飞书应用权限、DeepSeek Key 是我去开通配置的；
- 测试与文档在 AI 辅助下完成，但我逐条看过、能解释。

### 面试怎么讲（三句话）

1. 「这个项目解决的是 4S 店客服答不准、答不了的问题——答不准会担责，答不了客户就流失。」
2. 「我做的核心是业务层：69 条知识怎么分字段、什么情况必须转人工、工单 SLA 怎么定、看哪些指标判断好坏。」
3. 「代码是我用 AI 结对完成的，所以我能现场改阈值、加一条 FAQ、换一个演示数据；架构为什么这么选，我可以逐层讲。」

### 为什么这个角色定位反而加分

客户成功 / 实施交付岗要的是**能把客户问题翻译成方案**的人，不是手速快的程序员。这个项目证明的是：

- 知道一个客服系统该有什么字段、什么规则；
- 知道怎么衡量它好不好（三个指标联动看）；
- 知道答不上来时怎么兜底（转人工 + 回写）；
- 能用 AI 工具把想法快速变成能跑的东西——这是 2026 年最值钱的执行力。

## 五、常见问题

**Q：为什么知识库不直接喂给大模型？**
A：价格、保修、退订这些口径不能由模型自由发挥。现在是检索 + 证据 + 数字校验，模型只做改写。

**Q：为什么用 SQLite 不用 MySQL？**
A：单机演示、数据量小，SQLite 零配置；要并发时换 PostgreSQL，接口层已经隔离。

**Q：置信度是怎么算的？**
A：0.55×标准问题覆盖 + 0.25×同义问法覆盖 + 0.08×标签 + 0.05×答案 + 车型加权；覆盖度按「0.7×二字片 + 0.3×单字」算，容忍语序变化。

**Q：怎么防止 AI 乱答价格？**
A：三层：风险词直接转人工；答案必须带出处；大模型改写后校验数字必须在证据里，否则回退。

**Q：数据是真的吗？**
A：品牌和车型虚构，FAQ 按真实 4S 店话术整理，演示会话走真实链路生成。
